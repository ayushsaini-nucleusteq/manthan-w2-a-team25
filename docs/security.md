# Security

What the backend actually does today, and what it doesn't. Each control names the code or config that implements it.

## Implemented controls

| Area | Control | Where |
|---|---|---|
| Passwords | Stored as BCrypt hashes (Spring `BCryptPasswordEncoder`, cost 10). Never logged or returned. | `SecurityConfig.passwordEncoder`, `app_user.password_hash` |
| Sign-in | Unknown email, wrong password and inactive user all get the same 401 "Email or password is incorrect". Unknown emails are checked against a dummy hash so response time doesn't reveal which accounts exist. Every success and failure is audited (`LOGIN`, `LOGIN_FAILED` with the attempted email, never the password). | `AuthController.login` |
| Tokens | Stateless JWT, HS256, **8-hour expiry** (`exp`), signed with `JWT_SECRET` (must be at least 32 bytes or startup fails). Roles and the active flag are **re-read from the database on every request**, so a role change or deactivation takes effect immediately. | `JwtService`, `SecurityConfig.fromDatabase` |
| Authorization | Every `/api` endpoint needs a token except `POST /api/auth/login`. Role checks with `@PreAuthorize` per endpoint (403). Per-claim checks in the services: someone else's claim is **404 "Claim not found"** (US4-AC3), and acting on your own claim is 403. | controllers, `ClaimRepository.canView`, `ApprovalRouting.actAs` |
| Separation of duties | Nobody approves, rejects, sends back or sample-audits their own claim. Enforced in the service **and** by a database trigger on `approval_step`. | `ApprovalService.begin`, `V1__schema.sql` |
| Input validation | Bean Validation on every request body and parameter; money must match `^\d{1,10}\.\d{2}$`; expense dates not in the future; unknown fields rejected on PATCH; sort fields allow-listed; `LIKE` input escaped. | DTOs, `LineData`, `Sorts`, `ClaimRepository.like` |
| SQL injection | Parameterised SQL only (`JdbcClient` named parameters). Dynamic SQL is built only from server-side fragments. | all repositories and services |
| Concurrency | Row locks (`SELECT ... FOR UPDATE`) and `version` checks on claims, users and batches; advisory locks around submit (per employee and receipt hash), sample selection and batch creation; `UNIQUE (payout_item.claim_id)` so a claim can't be paid twice. | services, `V1__schema.sql` |
| Uploads | Max 5 MB (multipart limit plus a service check). Type is **sniffed from the bytes** (PDF / JPEG / PNG only), never trusted from the client. The server computes SHA-256. Storage keys are generated by the server (`claims/<id>/<uuid>`) and path-checked (no traversal). File names are sanitised. Downloads send `X-Content-Type-Options: nosniff` and a proper `Content-Disposition`. | `ReceiptService`, `ReceiptStorage`, `application.properties` |
| CSV export | Cells starting with `=`, `+`, `-`, `@` are prefixed with `'` (formula injection); commas and quotes are escaped. | `PayoutService.cell` |
| Errors | One `ApiError` shape. Messages are written by the app, **never stack traces, SQL or class names** (`server.error.include-*=never`, global exception handler). Every response carries `X-Request-Id`. | `GlobalExceptionHandler`, `ApiErrorController`, `RequestIdFilter` |
| CORS | Allow-list from `FRONTEND_ORIGIN`, only on `/api/**`; rejected origins get a JSON 403. | `CorsConfig` |
| HTTP headers | Spring Security defaults: `X-Content-Type-Options`, `X-Frame-Options: DENY`, `Cache-Control: no-store` on API responses. Sessions are stateless and CSRF is off (bearer tokens, no cookies). | `SecurityConfig` |
| Audit trail | Append-only: `BEFORE UPDATE/DELETE` and `TRUNCATE` triggers raise. No endpoint edits or deletes events. Every state change writes its event in the same transaction. | `V1__schema.sql`, `AuditService` |
| Secrets | Real values only in `.env` (gitignored). `.env.example` holds placeholders. Demo users' password comes from `SEED_USER_PASSWORD`. | `.gitignore`, `docker-compose.yml` |
| Container | Backend runs as a non-root `app` user; the JVM exits on OOM; the DB has no host port (only reachable on the compose network). | `backend/Dockerfile`, `docker-compose.yml` |

## Known limitations

- **No brute-force protection.** Failed logins are audited but not rate-limited, and accounts never lock.
- **Logout doesn't revoke tokens.** A token stays valid until it expires (8 h). There is no deny-list or refresh token.
- **HS256 shared secret.** If `JWT_SECRET` is empty, a random key is used per start: everyone is signed out on restart and keys aren't shared across instances.
- **Shared demo password.** All seeded users share `SEED_USER_PASSWORD`. Fine for the demo, not for real users. There is no password-change or reset endpoint.
- **The database user is a superuser in compose.** The migration's `REVOKE UPDATE/DELETE ON audit_event` has no effect on it; the triggers still block edits. A separate least-privilege app role is not set up.
- **Actuator is unauthenticated.** `/actuator/health`, `/info` and `/prometheus` are open on port 8080, so metrics are readable by anyone who can reach the port. Restrict the port or put a proxy in front outside local use.
- **No TLS.** The stack serves plain HTTP; TLS must be terminated in front of it.
- **Uploads are not virus-scanned.** Only type, size and hash are checked.
- **The audit log stores attempted emails** for failed logins (personal data). Retention is not defined.
